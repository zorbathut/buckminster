# Buckminster Architecture

Buckminster is a microkernel-inspired game engine: a Rust core under a flat C FFI, C# above it, shipped as a library that hosts embed. This document records the load-bearing decisions and conventions; the milestone-by-milestone build-out lives in PLAN.md.

## Governing principle: the default must be simple

The default way to write anything must be simple — sacrificing power and performance for simplicity where they conflict. Power and performance are retrofit paths: when a specific piece of a game needs to be fast, that piece gets fast-and-hard-ified, and the rest of the game stays easy. Mixed-speed codebases are the expected permanent state, not a transition, so the obligation cuts both ways: the easy path must have escape hatches reachable from inside it, and the fast path must tolerate slow code living next to it in the same game and the same frame. (Unity's DOTS-era ECS is the named anti-example: its fast-capable model was also fast-mandatory, which dragged every trivial thing into the hard model the moment one system needed speed.)

## Tier stack

Hosts own the loop — but only its *cadence*: the engine is a callee exposing `PumpEvents()` / `Tick(dt)` / `Render()`, and a desktop executable, a browser rAF callback, a Node script, or a test harness drives it. The granular calls are the engine's primitive seam (headless tests now, fixed-timestep later); production hosts will drive a core-provided frame composition built on those primitives rather than hand-composing pump/tick/render logic, so the hosts can't drift apart (the four-part model in PLAN.md's foundation decisions). Rust owns platform glue, windowing, the low-level WebGPU rendering layer, and kernel primitives (RIDs, logging transport), exported as flat `extern "C"` functions consumed via `[LibraryImport]`. C# owns the module registry, the engine object, the mesh/pass/dispatch layer, and everything above (the seeded PRNG, `RngStream`, landed C#-side in `src/general`) — code migrates C#→Rust only when profiling demands it. Three first-class run targets: `linux` (native), `web` (browser, emscripten), and `wasm-desktop` (the same emscripten build hosted by Node). Determinism — same inputs, same order, fixed dt, deterministic game code ⇒ bit-identical sim state — is a design contract from day one but not yet an active promise: there isn't enough engine to be deterministic yet (full rules and the status note in PLAN.md's Determinism section).

## FFI

Everything crossing the Rust↔C# boundary is flat `extern "C"` with blittable args, hand-written bindings on both sides.

**Entry-point wrapper**: every fallible `buck_*` export is a thin `extern "C"` fn whose body runs inside `ffi::guard` (`src/core/rust/ffi.rs`) — `catch_unwind` so no panic ever crosses the boundary, error-to-code mapping, and last-error storage. Exports return an `i32` `FfiCode` and write results through out-params. Out-params are non-null by caller contract and **unspecified on a nonzero return** — check the code before reading. Callback function pointers share the non-null contract, and more sharply: Rust declares them as non-nullable `fn` types, so a null there is an invalid value at the ABI boundary, not merely a pointer that must not be dereferenced. Codes: `0 Ok, 1 Panic, 2 CallbackError, 3 InvalidArgument, 4 EnginePoisoned` — defined in `ffi.rs`, hand-mirrored in `src/core/cs/Ffi/FfiCode.cs`, kept in sync manually; new codes append.

**`buck_last_error_message()`**: null if the last `buck_*` call on the calling thread succeeded; otherwise the error message, valid until the next `buck_*` call *other than `buck_last_error_message` itself* on the same thread — reading is non-destructive and repeatable. Callers copy immediately (`NativeMethods.LastErrorMessage()` does). This is the one deliberate exception to "every export runs inside guard": it is infallible, and routing it through the guard would clear the very error it exists to read.

**Callback rules** (from PLAN.md, non-negotiable): (1) callbacks are `[UnmanagedCallersOnly]` static methods passed as function pointers, never marshalled delegates; (2) no exception ever escapes a callback — every callback body is a try/catch wrapper; (3) static callback + u64 userdata key, no closures — `CallbackTable` (`src/core/cs/Ffi/CallbackTable.cs`) is the userdata registry, and the `[UnmanagedCallersOnly]` static recovers its target object from it by key; (4) Rust never holds a lock or borrow across a callback invocation. Plus the rail those four don't cover — **how a callback failure's detail reaches the original caller**: the callback's catch stashes the exception in `CallbackExceptionStash` (`src/core/cs/Ffi/CallbackExceptionStash.cs` — per-thread, take-semantics so a stale exception can't be misattributed later) and returns nonzero; Rust maps any nonzero callback return to `CallbackError` (preserving the value in the message); the original caller sees `CallbackError`, takes the stash, and rethrows. Callbacks mirror the export shape: `i32` code return, result via out-param.

**Bindings** (`src/core/cs/Ffi/NativeMethods.cs`): `[LibraryImport]`, keeping the native snake_case names for 1:1 greppability against the Rust exports — the friendly PascalCase layer is the M4 Engine's job. Raw FFI stays `internal`, never public API; tests reach it via `InternalsVisibleTo`.

**Native library wiring**: `src/core/cs/Buckminster.Core.csproj` copies `src/target/debug/libbuckminster_core.so` into the output dir (`None` + `CopyToOutputDirectory`, flowing transitively to test and host projects), with an explicit loud build error naming `./tool.bat build` when cargo hasn't produced it (skipped in IDE design-time builds so project load doesn't half-fail). The build tooling orders `build-dotnet` after both `build-rust` and `build-rust-wasm` for the same reason. (Cosmetic wart, accepted: the `.so` copy also flows into the wasm hosts' bin dirs, where it's inert — the classlib builds RID-less, so no per-target condition can scope it.)

**Errors are bugs; the log is the diagnostic** (the FFI-facing half of the PLAN.md foundation decision): `FfiCode` answers "did the FFI itself succeed" — panic, poisoned engine, callback failure, bad argument — and never grows domain entries; there is deliberately no machine-readable error taxonomy, no per-function error enums. A misused domain API fails soft (null RID / no-op) and emits a descriptive human-readable record through the log pipeline, which the exit-drain delivers synchronously at the causal call site; a host that wants hard failures installs a log sink that throws on Error records — strictness is host policy, not engine policy. The design-smell test: a caller probing errors to learn something (does this file exist, is this format supported) marks a missing explicit query interface, not a missing error code. Lifecycle-level caller bugs (bad config, stale handle) may still surface as exceptions from the friendly C# layer — the convention's force is on the resource/domain APIs from M6 on, and as built at M4 every existing API is lifecycle-level and fails hard.

**Wasm link story** (as built at M2; full pin/coupling detail in `docs/wasm-toolchain.md`): the core builds as a `wasm32-unknown-emscripten` staticlib via a per-invocation crate-type override (`cargo rustc --crate-type staticlib` — listing `staticlib` in Cargo.toml would make wasm builds attempt the cdylib link, which needs emcc; the archive needs no linker at all). Each wasm host links it via `NativeFileReference` — per-host because that item does not propagate through ProjectReference (dotnet/runtime #114724) — through the shared `src/WasmHost.props`, which also pins `WasmEnableExceptionHandling=true` to match Rust's wasm-EH unwinding. Panic containment (`catch_unwind`) works on all three targets. Two wasm-driven binding constraints are permanent: DllImport module names must exactly match a linked archive filename (the `lib` prefix is not stripped, hence the `buckminster_core.a` copy in `build-rust-wasm`), and **pinvoke signatures never use function-pointer types — callbacks cross as `IntPtr`** (mono's wasm interp-to-native path aborts on fn-pointer parameter types).

## Kernel (as built at M4)

**Engine lifecycle**: `Engine.Create(config, logSink)` → register modules → pump until `IsReady` → the host's tick/render loop → `Dispose`. Init is async-shaped from the foundation up (WebGPU device requests resolve only after control returns to the browser's event loop): module initialization runs inside the first `PumpEvents` — M4 completes it in one pump, but hosts must not assume that, and the host idiom is pump-and-tick until Ready (a pre-Ready `Tick` is a harmless no-op, so sim tick 0 stays pinned to Ready). The Rust side (`src/core/rust/engine.rs`) owns a registry of `Engine` structs whose FFI handles are real RIDs, so stale and reused-slot handles fail loudly from day one.

**Module registry**: modules implement `IModule`, declare dependencies by concrete type, initialize in stable topological order (registration order as tiebreak), and tick in pure registration order. Registration closes when init starts — including from inside a module's own `Initialize`. Failures are loud: cycles name the cycle path, missing dependencies name both parties, duplicate concrete types are rejected, and a failed init wedges the engine permanently (re-pumping would silently re-run the Initializes that succeeded before the failure — dispose and create a fresh one).

**Exit seam**: `Engine.QueueExit()` sets `ExitQueued`; the host loop condition is what honors it. Deferred by necessity, not politeness — the caller is typically a module mid-Tick, under the engine's own iteration, where synchronous teardown is impossible (GLFW `WindowShouldClose` lineage). The engine itself never acts on the flag; ticking past it is legal and fully functional. A future platform close event feeds into `QueueExit` rather than reading it; there is no Rust mirror because there is no Rust-side loop.

**Poison policy**: a panic caught inside an engine's scope poisons that one engine — every later call on it returns `EnginePoisoned` except `buck_engine_destroy`, which must keep working for teardown ordering. Poison is per-engine, and the containment runs inside the registry lock scope (an inner `catch_unwind`), so a panic can never poison the Rust-side mutex itself.

**Teardown ordering** (load-bearing, both directions): `Dispose` destroys FIRST — destroy's own exit-drain delivers the buffered log tail, including records logged by destroy itself, through the still-registered sink — then clears the sink registration and unregisters the callback key in a finally. `Create`'s failure path is the mirror image: clear the Rust sink registration first, then unregister the key, then destroy — reversed, a dangling registration with a dead key breaks every subsequent create in the process.

**RID allocator** (`src/core/rust/rid.rs`): the generational slotmap behind every Rust-side object handle. u64 layout: 32-bit slot index, 8-bit allocator type tag, 24-bit generation; raw 0 reserved as null. Ported from Godot's `rid_owner.h` with deliberate deviations — per-slot generations instead of Godot's process-global counter (whose stale detection wraps program-wide), the type tag actually stored in the RID (Godot's type safety is which-owner-you-ask, by convention), and a plain `Vec` of enum slots instead of lock-free chunked storage we don't need. Lookups return `Option`; stale or mis-tagged frees are loud errors; the free list is LIFO and its reuse order is a pinned determinism contract; a slot whose generation space is exhausted is retired rather than ever aliasing; dropping an allocator with live entries prints a leak report to stderr. One shared implementation, instantiated per subsystem, never shared across subsystems — sim-visible RID values must not depend on render-side allocation timing.

**Layout-assertion seam**: `EngineConfig` is the first hand-mirrored `#[repr(C)]` struct, and `buck_layout_engine_config` exports its size and field offsets for a C# test comparing `Marshal.SizeOf`/`OffsetOf` on every target — the interim protection until FFI binding generation exists (deferred list), and its output check afterward.

## Logging

One pipeline, both languages through one path: Rust logs via the `log` crate; C# logs via the public `Log` facade (`Log.Error/Warn/Info/Debug/Trace`, plus `Log.Ex(exception)` for the full-detail dump) over `buck_log` — one buffer, one ordering, one filter, one delivery path, and a C# record is delivered synchronously within its own `Log` call. Two delivery channels:

- **The immediate channel** (stderr today) fires at emit time under its own threshold (`EngineConfig.LogStderrLevelMax`, independent of the buffer filter): zero-latency and crash-proof, and the seam where future network error reporting or an editor-over-socket attaches.
- **The registered sink** (the C# callback `Engine.Create` requires) is delivered by the **exit-drain at the tail of every `buck_*` call** (`ffi::guard`) — the point where every Rust lock and borrow is provably released but the causal C# call is still on the stack, so an engine error surfaces at the buggy call with an accurate C# stack. Buffering rather than a synchronous callback per statement is what keeps callback rule 4 honest: a `log::info!` deep inside borrowed engine state must not re-enter C#.

Delivery rules, each pinned by test: records-before-result (a failed or panicked call's diagnostics deliver before its failure surfaces — in-order error reporting is guaranteed); the body's outcome wins the return code over a drain failure; the thread-local last-error is written last, so a sink that re-enters the FFI during delivery can't clobber the failing call's message. The drain additionally runs under its own `catch_unwind` and a reentrancy scope guard — defensive rails on paths the managed side can't currently reach, so those two are not test-pinned. Loss is always loud: overflow drops oldest and the next drain leads with a synthesized drop report whose count persists until actually delivered; a throwing sink surfaces its exception from the emitting call and loses only the record it threw on (redelivery would be a poison pill), with the undelivered tail redelivered ahead of fresh records at the next call's exit. The sink is mandatory at `Create` — silent log dropping is banned; a host that truly wants to discard logs writes that decision down as a discarding delegate. Calling `Log.*` before any engine has configured logging is a loud error, never silence. Config and sink registration are process-scoped last-wins (the `log` crate's logger is a process global; multi-engine log separation is a non-goal — `Engine.Current` at delivery time is the routing key if per-engine routing ever earns its way in).

## Threading model

Multiple simultaneous `Engine` instances are supported. A single engine's calls must be externally synchronized — never concurrent, though alternating threads under that rule is legal. *Different* engines may be driven concurrently from different threads: per-call FFI state is per-thread (last-error, exception stash, drain flag) and the shared registries are locked (the Rust engine registry, the log buffer, `CallbackTable`). `Engine.Current` is the thread-local ambient engine (Ghi `Environment.Current` lineage): `PumpEvents`/`Tick`/`Render` scope it to themselves with save-and-restore, so module callbacks and log-sink deliveries see the right engine without handle-threading; hosts may set it directly; unset reads are null. It is per-thread explicitly — thread B never sees thread A's `Current`. The sharpest consequence, pinned: with concurrent engines, the process-global log sink is invoked concurrently from multiple threads — **the sink must be thread-safe, and cross-thread record ordering is unspecified**. (Sim-level parallelism is a separate future topic — PLAN.md's clonable-state and threading entries.)

## Repo layout

The root directory is a map of the repo, kept uncluttered: entry points (`tool.bat`, `SConstruct`, `Buckminster.slnx`), user-facing documentation, and the `src/` and `tools/` trees. Infrastructure files live down inside the tree they serve, not at the root. The one exception is `global.json`: the .NET SDK resolver and IDEs discover it by walking up from wherever `dotnet` runs, so it must sit at (or above) the solution — moving it into `src/` would silently unpin root-invoked builds. It also carries the `dotnet test` runner opt-in (Microsoft.Testing.Platform).

Source lives under `src/`, organized by module — not by language. `src/` itself holds the cross-module build files: the Cargo workspace (`Cargo.toml`, `Cargo.lock` — discovered by walking up from the crates), `rust-toolchain.toml` (discovered differently: rustup walks up from the *cwd of the cargo invocation*, so cargo must run with cwd inside `src/` — the build tooling does, and CI steps must too; a root-cwd invocation using `--manifest-path` would silently use the machine's default toolchain instead of the pin), and the shared MSBuild properties (`Directory.Build.props`, discovered by walk-up from each project). IDE note: JetBrains attaches the nested Cargo workspace automatically; VS Code's rust-analyzer needs `rust-analyzer.linkedProjects` pointed at `src/Cargo.toml`, and pylance won't auto-find the pyright config (`[tool.pyright]` in `tools/lib/pyproject.toml`) from a root workspace — `./tool.bat check` remains the enforcement path regardless. A module directory contains language subdirs: `rust/` (crate root via a `[lib] path` override in the module's `Cargo.toml`), `cs/` (one C# project), `tests/` (test projects; Rust unit tests live in the crate, and cargo integration tests would also land in `tests/` next to `Cargo.toml`). A module may be single-language; hosts follow the same convention. The one deliberate exception: the cross-cutting C# test suite lives top-level at `src/tests/cs` because it tests multiple libraries and feeds a single source glob into the wasm hosts — per-module `tests/` remains the rule for language-local tests (core's Rust integration tests follow it).

Current modules:

- `src/core` — the engine core, one conceptual unit spanning both languages: `rust/` (crate `buckminster-core` — kernel primitives, FFI rails, logging transport) and `cs/` (assembly `Buckminster.Core` — the managed engine surface: Engine, module registry, Log, FFI bindings). Namespaces are `Buckminster` and `Buckminster.Ffi`, and grow by topic (`Buckminster.Render`, …), not by module or assembly — the module split is a repo-organization detail.
- `src/general` — C#. Commonly-used managed code that isn't strictly part of the minimum core (assembly `Buckminster.General`, namespace `Buckminster`; RngStream lives here). It may reference Core — it sits directly above it — but never does its own FFI; anything above core may depend on it, modules and usergames included.
- `src/usergame-demo` — C#. The four-part model's usergame, demo edition (assembly and namespace `Buckminster.Usergame.Demo`): two modules with a real dependency, run by the desktop host to 100 ticks; statically linked into the host as the degenerate case of usergame loading.
- `src/tests` — the cross-cutting C# NUnit suite (`cs/`, assembly `Buckminster.Tests`), covering core, general, and the demo usergame; see the layout-convention exception above.
- `src/host-desktop` — C#. The desktop host executable (`Buckminster.Host.Desktop` assembly, `Buckminster` namespace consumer).
- `src/host-web` — C#. The browser host (`Buckminster.Host.Web`): wasmbrowser-template shape, renders through `[JSExport]` + `wwwroot/main.js`.
- `src/host-wasmnode` — C#. The Node-hosted wasm host (`Buckminster.Host.WasmNode`, the `wasm-desktop` run target): the same `browser-wasm` build run by Node via `runtimeconfig.template.json`. Shared wasm-host build wiring (native staticlib link, EH pin, loud missing-archive check) lives in `src/WasmHost.props`.

Tests are NUnit on every target — through the Microsoft.Testing.Platform runner natively, and inside the wasm hosts by running the real NUnit engine in-process (`NUnitTestAssemblyRunner` from `NUnit.Framework.Api`, wrapped by `src/tests/cs/RunnerWasm.cs`). Two package settings make the engine single-thread-safe: `RunOnMainThread` (synchronous work-item dispatch) and `SynchronousEvents` (no EventPump thread). NUnitLite was evaluated and rejected for wasm, but its blockers (event-pump thread, Console redirection, Environment.Exit) are runner-layer, not framework-layer — the engine itself runs fine; approach proven in-browser by planefarer6. See the test-matrix table in Build tooling.

## Build tooling

One entry point: `./tool.bat <command>` (the same file runs under sh and cmd). It verifies and self-heals the tools environment (a poetry-managed venv at `tools/lib/.venv`), then dispatches to `tools/<command>.py`. Every `tools/*.py` is a command — support code and env config live in `tools/lib/`, imported as `from lib import ...`. Current commands: `build`, `test` (the quick native slice), `test-all` (the full matrix below), `check` (pyright strict + `cargo fmt --check` + `cargo clippy -D warnings`), `serve` (build, then run the browser host's dev server until Ctrl+C). Build targets: `build-rust` (native), `build-rust-wasm` (the emscripten staticlib), `build-dotnet` (the solution, whose wasm hosts perform the emcc link — so a toolchain mismatch fails the default build, by design).

**The test matrix** (`./tool.bat test-all`; every cell ran a deliberately-failing test visibly red at M3 — the harnesses' failure paths are proven, not assumed):

| Suite | linux | wasm-desktop (Node) | web (browser) |
|---|---|---|---|
| Rust (libtest) | `cargo test` | `cargo test --target wasm32-unknown-emscripten`, PATH node as the cargo runner | same test binaries in a generated DOM-sentinel page, headless Chrome via CDP (`tools/lib/wasmbrowser.py`) |
| C# (NUnit) | `dotnet test` (MTP runner) | RunnerWasm in `Buckminster.Host.WasmNode`, exit code via `runMainAndExit` | RunnerWasm in `Buckminster.Host.Web`, DOM sentinel via the same driver |

Plus one row outside the language×target grid: `cs-desktop-host` runs the built desktop host end to end (the demo usergame to 100 ticks) and requires exit 0 AND the exact `BUCK-DEMO-EXIT ticks=100` sentinel line — exit-0-without-the-demo-provably-running is not a pass, and both failure paths were proven red.

No per-target exclusions, and no per-target feature subset: RunnerWasm runs the same NUnit engine `dotnet test` does, so `[SetUp]`, `[TestCase]`, `[Values]`, `Assert.Multiple`, etc. work on every cell (`NUnitFeatureTests` pins this permanently). Loudness guards, each proven red: discovery failures are detected via the suite's `RunState` (NUnit swallows discovery exceptions into an invalid suite), a zero-test run is a hard error, and the executed case count is cross-checked against discovery's count so silently-dropped tests fail the run. Known wasm hazards, all loud: a genuinely-async test deadlocks under `RunOnMainThread` (killed by the node cell's subprocess timeout or the browser driver's timeout); `[RequiresThread]` throws `PlatformNotSupportedException`; and the browser cell fails past ~30s of synchronous execution (the CDP driver's per-command timeout — escalation path is per-fixture JSExport chunks, planefarer-style). The browser rows require Chrome/Chromium (hard FAIL with instructions when absent — a skippable target is a silent downgrade). The wasm hosts compile the test sources in as linked files and run them in-host; that runner role is permanent (the M3-era note that M4 would "revert" them to hosting was wrong) — real browser hosting lands alongside it when the web render target (M7) needs it, not by replacing it, and the Node cell stays render-less regardless (no WebGPU under Node).

- **Install floor**: git, Python 3.10+, and platform C++ build tools (MSVC Build Tools on Windows — Rust's linker needs them anyway). Everything else is auto-provisioned user-local (rustup into `~/.cargo`/`~/.rustup`, the .NET SDK into `~/.dotnet` when no satisfying SDK exists) or audited with exact install instructions (`tools/lib/toolchains.py`). The .NET wasm-tools workload auto-installs when the SDK root is user-writable and is audited-with-instructions otherwise (never auto-sudo), with a warn-only emscripten version drift tripwire; node presence is audited with a version tripwire.
- **Pins**: `rust-toolchain.toml` (exact Rust version; honored because cargo is always resolved through rustup, never trusted from PATH), `global.json` (.NET SDK band; arbitration is always delegated to the SDK resolver itself), `tools/lib/poetry.lock` (python tooling), package versions in csproj files.
- **Orchestration**: SCons owns the coarse meta-DAG (tool invocations, and later the shader pipeline, wasm link assembly, codegen, packaging); cargo and MSBuild remain the fine-grained inner build systems. All build code is Python checked by pyright (`./tool.bat check`, CI-enforced from M3) in strict mode, with exactly two scoped exemptions: the root `SConstruct` (an untyped logic-free shim — SCons injects globals pyright can't model) and `tools/lib/sconsfacade.py` (checked at basic mode — it's the quarantine for all SCons type suppressions, since SCons ships no type information, and the migration seam if SCons is ever replaced). Target definitions live in `tools/lib/buildtargets.py`, fully strict, touching SCons only through the facade.
- rustfmt and clippy run with default configurations — no config files; gates land with CI in M3.

## Conventions

Pinned before line one of math code; uniform everywhere:

- **Coordinates**: right-handed, **Y-up**, −Z forward (glTF-compatible).
- **Units**: meters, seconds, radians.
- **Matrix/vector semantics**: glam conventions (column vectors, column-major storage) on the Rust side; C# mirrors glam semantics. `System.Numerics` types may be used for storage/SIMD, but the documented convention is glam's — any transposition responsibility gets pinned in writing at the boundary that incurs it.
- **Depth**: 0..1 clip range (WebGPU native). Reversed-Z is deferred but anticipated: nothing may bake in "near = 0".
- **Ranges are `[closed, open)`**, uniformly. Anything needing inclusive semantics converts at the call site, never inside shared utilities. Adjacent ranges must not double-count their shared edge; the uniformity is the point.
- **Vendored/forked code carries provenance**: a `VERSION.txt` recording the source repo + commit, why it's forked, what changed, and a "re-import from upstream rather than reimplement" pointer — plus symmetric `// BUCK BEGIN <desc>` / `// BUCK END <desc>` markers around every local patch to vendored code, so patches survive upstream upgrades.
