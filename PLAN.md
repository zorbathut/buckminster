# Buckminster Implementation Plan

Working plan for getting the engine from empty repo to a working foundation: the Rust↔C# FFI, three run targets with tests running on all of them, a deterministic kernel with a replay-verification harness, WebGPU rendering with golden tests, and a mesh/pass/dispatch layer on top. Milestones are ordered by risk: the scary unknowns (FFI, wasm linking, test infrastructure everywhere, WebGPU-everywhere) get proven first, on the smallest possible amount of code.

Reference material: a Godot checkout lives at `../godot` and planefarer (the owner's shipped-game codebase, whose patterns this plan repeatedly cites) at `../planefarer`, with Dec also standalone at `../dec`. **All of these may be yanked from, not just referenced** — code, patterns, whole files — they're either the owner's own work or MIT-licensed (owner's statement; attribution per license where applicable). Specific known-good starting points: `../godot/core/templates/rid_owner.h` (the RID allocator we're stealing), `../godot/servers/display/display_server.h` (windowing/event API vocabulary), `../planefarer/project/thirdparty/q32/` (fixed-point math), `../planefarer/project/thirdparty/ghi/` (environment/CoW ancestry), `../planefarer/tools/` + `tool.bat` (the tool-entry-point pattern), `../planefarer/CLAUDE-Orrery.md` (whole-environment parallelism design).

## Locked-in foundation decisions

These were settled in design discussion and are the load-bearing choices; everything else is deferrable.

- **The default must be simple to write.** The governing API principle, and it outranks the others: sacrifice power for simplicity, sacrifice performance for simplicity — in the default path. Everything is easy-to-write-and-slow by default; when you decide to care about a specific piece, you fast-and-hard-ify *that piece*, and the rest of the game stays easy. Mixed-speed codebases are the expected normal state, not a transition: per the 80/20 (or 95/5) rule, most code never earns optimization, and the engine must respect "ehhh, it'll be fine, I'll fix it later" as a legitimate permanent stance. That imposes a two-sided obligation — the easy path must have escape hatches reachable from inside it, *and the fast path must tolerate slow code living next to it*, same game, same frame. Unity's ECS is the named anti-example, and its worst sin is the second side: the fast-capable model was also fast-*mandatory* — no slow-easy path inside DOTS, so one hot system dragged every trivial thing into the nightmare model, forcing a day-one, game-wide, all-or-nothing architecture decision with no bridge. Existing decisions already follow this shape (deterministic by default with opt-in perf modes, chatty FFI for one-time ops with bulk calls only where per-frame) and every future API gets held to it — most of all the M9 layer and the eventual environment/clone system.
- **Tick-as-callee.** The engine never owns a loop. Hosts (desktop exe, browser rAF callback, Node script, test harness) call `PumpEvents()` / `Tick(dt)` / `Render()`. Tick and Render are separate calls even though desktop always pairs them — that seam is what makes headless tests and fixed-timestep work later.
- **Three run targets, first-class from M2 on.** `linux` (native), `web` (browser, emscripten build), and `wasm-desktop` (the *same* emscripten build hosted by Node — wasm iteration and CI without a browser). Every milestone keeps all three green; a feature that can't exist on a target (e.g. WebGPU under Node) gets an explicit per-target note, never silence. Windows is a build-check target via CI, not part of the daily matrix.
- **RID handles.** Every Rust-side object crossing the FFI boundary is an opaque u64: index + generation + a few type-tag bits, Godot-style. One shared allocator *implementation*, instantiated per subsystem — allocator instances are never shared across subsystems, because sim-visible RID values must not depend on render-side allocation timing (async init makes render-side call order nondeterministic run-to-run; see Determinism). Lookups return `Option`; stale handles fail loudly, never alias.
- **Callbacks, done safely.** Rust→C# callbacks are allowed and used freely (pull-based event buffers are a per-subsystem optimization for later, if ever). Four rules, non-negotiable: (1) `[UnmanagedCallersOnly]` static methods passed as function pointers, never marshalled delegates; (2) no exception ever escapes a callback — every callback body is a try/catch wrapper; (3) static callback + u64 userdata key, no closures; (4) Rust never holds a lock or borrow across a callback invocation.
- **FFI shape.** Flat `extern "C"` functions, `[LibraryImport]`, blittable args only. `catch_unwind` at every Rust entry point; errors are return codes + `last_error_message()`. Anything per-frame-per-object is a bulk span call from day one; one-time operations may be chatty. Bindings hand-written until the shape stabilizes; the successor (binding generation from Rust source, including C#-implemented traits) is designed in the deferred list.
- **Errors are bugs; the log is the diagnostic.** The FfiCode return answers "did the FFI itself succeed" (panic, poisoned engine, callback failure, stale handle) and never grows domain entries; there is deliberately NO machine-readable error taxonomy — no per-function error enums, no `BUCK_BUFFER_CREATE_ERR_INVALID_SIZE` tables — because nothing should ever be written that switches on error detail. A misused API call fails soft (null RID / no-op) and emits a descriptive human-readable record through the log pipeline, whose exit-drain delivers it synchronously at the causal call site (and the stderr echo has it even earlier), so fail-soft stays debuggable; a host that wants hard failures installs a log sink that throws on Error records, turning every engine error into an exception at the buggy call — strictness is host policy, not engine policy. The design-smell test: if a caller wants to probe errors to learn something (does this file exist, is this format supported), that is a missing explicit query interface, not a missing error code. Lifecycle-level caller bugs (bad config, stale handle) may still surface as exceptions from the friendly C# layer — the convention's force is on the resource/domain APIs from M6 on.
- **Wasm link story.** Rust builds as a staticlib for `wasm32-unknown-emscripten`, linked into the .NET wasm publish via `<NativeFileReference>`. The coupling is three-way, not two-way: rustc ships a *prebuilt* std for the emscripten target (with a specific unwinding ABI) which must be compatible with the emsdk the .NET workload uses. rustc + emsdk + .NET SDK are pinned as a matched set and re-verified by actually linking and running the walking skeleton whenever any of them bumps.
- **Rendering Low-Level = webgpu.h.** The RLL codes against the standard `webgpu.h` C API from Rust: wgpu-native supplies it on desktop, emdawnwebgpu supplies it on web. One RLL code path, two vendors. (Dawn-native-on-desktop stays available as a fallback if wgpu-native diverges too much from the shared header.)
- **Engine init is async-shaped.** WebGPU adapter/device requests are async-only in the browser (the promises resolve only after control returns to the event loop, and the .NET wasm build can't assume JSPI/Asyncify). So init never blocks: the host calls `Create`, then keeps pumping `PumpEvents`/`Tick` until the engine reports Ready. Costs a trivial poll loop on desktop; makes web work at all. This fits tick-as-callee — nothing else would.
- **Shaders in HLSL.** Offline build step: HLSL → DXC → SPIR-V → Naga → WGSL. WGSL is what gets fed to the RLL on every platform (it's the one format both vendors accept natively). HLSL stays inside the WebGPU-expressible subset.
- **Language split, initially.** Rust owns: platform glue, windowing, RLL, RID/kernel primitives. C# owns: module registry, engine object, the mesh/pass/dispatch layer, and everything above. Note the language split is orthogonal to the determinism boundary: C# is not sim-only — a lot of C# is expected to be render code, UI code, and other non-sim engine/game code (the mesh/pass/dispatch layer itself is C# render code). Sim-side rules attach to a piece of code's *role*, never its language. Code migrates C#→Rust later as profiling demands, not speculatively — with one standing constraint: *sim-side* code that migrates must keep its state inside the environment, or provide deterministic snapshot/restore across the FFI. A future Rust sim system (physics, pathfinding) with private internal state would silently break clone/checksum/replay. Render-side and platform code migrates freely.
- **Modules are compile-time composition.** No dlopen (web forbids it anyway). Rust modules are cargo features/crates; C# modules are assemblies/classes registered at startup with declared dependencies, initialized in topological order.
- **The current abstraction ceiling is meshes/passes/dispatch.** No lighting, no cameras, no "renderer" in the Forward/Deferred sense — the plan ends at a layer where you make meshes and passes and dispatch them. The shape of that layer gets designed interactively with the project owner (who has strong opinions about it) before implementation, not autonomously.
- **Determinism is a hard engine property.** Same inputs in the same order + fixed dt + deterministic game code ⇒ bit-identical sim state. The engine is never the source of nondeterminism. Full rules and scope in the Determinism section below.

## Determinism (hard requirement)

Same inputs in the same order + a fixed dt + deterministically-written game code ⇒ bit-identical sim state, every run, reliably. The engine's side of the contract is that *it* is never the source of nondeterminism; the coder's side is writing deterministic game code (and accepting that a variable dt gives variable results — that's fine and expected). A more-efficient nondeterministic mode may exist someday (see the threading entry in the deferred list); deterministic is the default.

**Scope of the promise, v1: bit-exact replay on the same build, target, and machine/environment.** "Same machine" is load-bearing, not caution: even a single Linux binary can diverge across machines, because glibc dispatches `sin`/`cos`/`pow` to CPU-specific implementations at load time (and changes results across glibc versions), .NET BCL numeric helpers branch on `Vector128/256/512.IsSupported` and `Vector<T>.Count` varies per CPU, and tiered JIT compilation has historically changed float results mid-process. What widens the promise to cross-machine — and eventually cross-target (linux ↔ wasm ↔ windows) — is deterministic sim code holding stricter rules: no platform libm, no hardware-width-dependent vector helpers, ordinal-only string comparison, and the heavy hammer that makes the rest mostly moot: **avoiding float in deterministic sim entirely, in favor of fixed-point or softfloat**. Planefarer (`../planefarer`) has working prior art: `project/thirdparty/q32/Q32.cs` (Q32.32 fixed-point with trig/sqrt) and `Vector2Q`/`Rect2Q` on top. The deterministic-sim-math deferred entry owns this; nothing before it promises cross-machine.

Engine rules — each is policy from day one, because determinism is cheap to hold and brutal to retrofit:

- Sim never reads the wall clock or any ambient process state (env vars, locale, CPU features…). Time is the host-provided dt and tick counters derived from it. (Ambient in the OS sense — the thread-local current-*Buckminster*-environment global from the clonable-state design is fine; it's sim state, not the outside world.)
- All engine randomness comes from seeded PRNG streams. The kernel provides the algorithm and stream creation; stream **state** is sim-state-resident — included in the state hash, cloned with the state — so future clones carry their randomness with them and the harness catches PRNG misuse for free. OS entropy never touches sim paths.
- No sim-observable behavior may depend on hash-map iteration order. Rust: default `HashMap` hashing is randomized per map *instance* — sim-visible maps use deterministic ordering (`BTreeMap`, `IndexMap`, or a fixed-seed hasher). C#: `Dictionary` order is unspecified, `string.GetHashCode` is randomized per *process*, and object identity hash codes vary per run — none of these may key or order anything sim-visible; the engine provides a deterministic hash utility for when game code needs one.
- Stable sorts (or total-order keys) in sim-affecting paths.
- Event delivery order is defined and reproducible, and the replay format is the **full host-call trace** — the dt sequence and injected events, in order; `Tick(dt)` calls are inputs too, and where events fall relative to ticks is part of the recording. Sim tick 0 is pinned relative to Ready. (This is why the M5 host-injectable event surface matters beyond testing.)
- Engine-internal async completions (device ready, future asset loads, error callbacks — anything whose timing depends on drivers or threads) are either sim-invisible or delivered through that same recorded/replayed stream. Nothing with nondeterministic timing touches sim except as recorded input.
- RID allocation is deterministic given deterministic call order — the slotmap free-list is deterministic; nothing randomizes it — and sim-visible RIDs come only from allocator instances whose *entire* call order lies inside the determinism boundary. Render-side allocation (whose timing async init makes nondeterministic) uses separate allocator instances, and its RIDs never enter hashed sim state.
- Rendering never feeds back into sim. GPU output (readbacks, timings, query results) is test/tooling-side, or explicitly treated as external input that the game must handle like any other nondeterministic input.
- Generalizing that: **a sim tick is a pure function of (environment state, recorded input trace)**. During a tick, game code may *emit* outward freely — draw lists, sound requests, log records, events to the host — but never reads back from any engine service: not render, not audio, not window, not clock. Anything an engine service needs to tell sim arrives as recorded input on a later tick. This rule is also what makes clone-and-run-parallel possible at all: a sim tick touches nothing shared.
- The engine **enforces** that boundary at runtime instead of trusting discipline: engine services refuse sim-context access via a tick-scoped lockout. Planefarer had to patch this into its Godot fork (`Input.SetInputAccessForbidden` wrapped around every tick); Buckminster owns the engine, so every service gets it for free — "sim read the mouse" becomes an immediate error, not a desync three weeks later.
- Finalizers/`Drop` never mutate sim state — they're for resource cleanup, and their timing is nondeterministic by nature. More generally, sim never observes GC state (`WeakReference.IsAlive`, `GC.GetTotalMemory`, resurrection tricks).
- Sim code sticks to plain IEEE arithmetic: no fast-math flags anywhere, ever; engine sim paths avoid platform libm transcendentals (an engine sim path that needs `sin` uses the deterministic implementation — deferred list — or doesn't exist yet). NaN bit patterns are nondeterministic on wasm by spec: NaN in sim state is treated as a bug, and the state hasher **fails loudly on NaN** — that is the enforcement mechanism. (NaN canonicalization is a cross-target tool for later; in v1 it would hide exactly the divergence it papers over.)

Verification: the determinism harness, built in M4 and grown forever after — run the same input trace twice, hash the sim state every tick, compare bit-exactly. Crucially, **twice means two separate processes** (the harness writes its per-tick hash trace to a file; the test diffs two runs): .NET string hashing is randomized per process, so an in-process double-run would silently pass on exactly the hash-order bug class the rules name. Hashing is content-based — never identity-, address-, or allocation-incident-based — because this same convention grows into the cross-platform state checksum (see the clonable-state deferred entry). Like the golden-test infra, the harness is first-class: every sim-side feature lands with its state covered by the hash.

## Conventions to pin in ARCHITECTURE.md at M0

Written down once, before line one of math code:

- Right-handed world coordinates, **Y-up**, −Z forward (glTF-compatible).
- Units: meters, seconds, radians.
- glam conventions on the Rust side (column vectors, column-major storage); C# mirrors glam semantics. `System.Numerics` types may be used for storage/SIMD but the documented convention is glam's — transposition responsibilities pinned in writing at the boundary.
- Depth: 0..1 clip range (WebGPU native). Reversed-Z deferred, but noted so nothing bakes in "near=0".
- Ranges are `[closed, open)`, uniformly; anything needing inclusive semantics converts at the call site, never inside shared utilities. (Planefarer rule, imported wholesale — adjacent ranges must not double-count their shared edge, and the uniformity is the point.)
- Vendored/forked code carries provenance: a `VERSION.txt` recording source repo + commit, why it's forked, what changed, and a "re-import from upstream rather than reimplement" pointer (planefarer's clipper2 fork is the model), plus symmetric `// BUCK BEGIN <desc>` / `// BUCK END <desc>` markers on every local patch to vendored code so patches survive upstream upgrades (planefarer's `DH BEGIN/END` convention).

## Milestones

Each milestone ends with all tests green on every target they apply to, and a CHANGELOG entry. Nothing in a later milestone starts until the earlier one's exit criteria pass, except where noted as parallelizable.

### M0 — Repo scaffolding

1. Everything under `src/`, organized **by module, not by language**; a module directory holds language subdirs (`rust/` via a `[lib] path` override, `cs/`, `tests/`). Cargo workspace lives at `src/` (the repo root stays a map: entry points and user-facing docs only, infrastructure down in the tree it serves); single crate `src/core` (`buckminster-core`) for now (more modules spin off as we go, per YAGNI).
2. .NET solution at the repo root (`Buckminster.slnx`): `src/stdcs` (managed core library — assembly and root namespace `Buckminster`; namespaces grow by topic, not by module), `src/host-desktop` (`Buckminster.Host.Desktop`, the ~20-line loop), `src/stdcs/tests` (`Buckminster.Tests`).
3. `ARCHITECTURE.md` with the default-must-be-simple design principle, the conventions above, and a one-paragraph description of the tier stack.
4. Toolchain pins: `rust-toolchain.toml`, `global.json`, rustfmt/clippy defaults confirmed.
5. Single tool entry point, planefarer-style: one polyglot `tool` script (bash+batch in one file, runs everywhere). Its two jobs: (a) the **single point of entry that verifies and initializes environment setup** — toolchain presence, pinned versions, self-healing of the tool environment itself — before dispatching to any command, and (b) a `tools/` directory structured so per-command scripts **share common code** rather than copy-pasting. Everything later — `test-all` (M3), shader builds (M8), deploy — lands inside it instead of accreting ad-hoc scripts. Start tiny (build + test commands); the structure is what's being established.
   **Install-requirement policy**: minimize what a fresh machine must install by hand, and the toolchain *audits* the rest — every dependency is either auto-provisioned user-local by the bootstrap (pinned versions, no admin rights: rustup via `rustup-init` + `rust-toolchain.toml` auto-installing the pinned toolchain and wasm target; .NET SDK via the official `dotnet-install` scripts + `global.json`; workloads via `dotnet workload install`; emsdk from the workload itself; DXC/Naga/wgpu-native as fetched prebuilt artifacts) or checked-and-explained with exact install instructions on failure. Target floor, planefarer-grade: git + Python + platform C++ build tools (MSVC Build Tools on Windows — Rust's linker needs them anyway), then "run the build script."
6. Build orchestration: **SCons, with typing enforced** — decided after surveying the field (no mature generalized file-DAG framework exists in Rust or C#; ninja-generators handle dynamic dependencies poorly; Buck2/Bazel fight the .NET wasm workload's MSBuild-owned build; Shake is the right shape in the wrong language). cargo and MSBuild stay the inner, fine-grained build systems; SCons owns the coarse meta-DAG (tool invocations, shader pipeline, wasm link assembly, codegen, packaging). De-footgunning discipline: pyright strict mode CI-enforced on all build code, and the SCons API accessed only through a small typed façade module — which is both where the type-ignores are quarantined and the migration seam if SCons ever needs replacing. SCons + Python pinned via the `tool` bootstrap.

**Done when:** `cargo build` and `dotnet build` both succeed on an empty-but-real skeleton (via the tool entry point); ARCHITECTURE.md exists.

### M1 — FFI walking skeleton (desktop)

The point: prove the entire FFI discipline on a function that does nothing, so every later API lands on rails.

1. Rust `cdylib` exporting `buck_add(a, b)` behind the standard entry-point wrapper: `catch_unwind`, error-code return, `buck_last_error_message()`.
2. The entry-point wrapper itself (macro or helper fn) — this is a deliverable, not a detail; every future export uses it.
3. C# `[LibraryImport]` bindings + native library build/copy wiring so `dotnet test` finds the `.so`/`.dll`.
4. Callback round trip: C# registers an `[UnmanagedCallersOnly]` static + userdata key, Rust invokes it, C# side recovers its object from the key table. Include the deliberate-panic and deliberate-exception tests — prove both directions of "no unwind across the boundary".

**Done when:** `dotnet test` exercises add + callback + error paths + panic containment, green on Linux (Windows verified when the Windows CI build check exists, M5).

### M2 — Wasm walking skeleton, both wasm hosts

Highest-risk unknown in the project; do it before any engine code exists to throw away. This is also where all three run targets come alive.

1. .NET wasm browser project (`wasmbrowser` template) under `src/host-web` (`Buckminster.Host.Web`), and a Node-hosted wasm project (`wasmconsole` template) under `src/host-wasmnode` (`Buckminster.Host.WasmNode`) — the `wasm-desktop` target. Same emscripten build, two hosts.
2. Rust staticlib built for `wasm32-unknown-emscripten` using the Emscripten shipped in the .NET workload; linked via `<NativeFileReference>`.
3. Same `buck_add` + callback round trip running on both wasm hosts: Node prints the value to the terminal, browser renders it into the page.
4. `docs/wasm-toolchain.md`: the rustc/emsdk/.NET-SDK pin triple (including the unwinding-ABI dimension — rustc's prebuilt emscripten std must match the emsdk's exception-handling mode), how to find the workload's emsdk, and the re-verification checklist for bumps. This doc must also cover how *cargo* finds that same emsdk: M3's Rust wasm tests link executables (not just a staticlib), so cargo/emcc is a second emsdk consumer that must resolve to the pinned version — it isn't on cargo's PATH automatically. Also record the `wasmconsole`/`wasmbrowser` template install channel (the templates package, installable via `dotnet new install` — see risks). Verification means linking and running the skeleton, not comparing version strings — the build script's job is to make a mismatch fail at M2 size instead of M6 size.

**Done when:** a value computed in Rust, called from C#, including a callback round trip, shows up in the terminal (Node) and the browser page. This milestone is allowed to be ugly; it exists to de-risk, and gets cleaned up as later milestones touch it.

### M3 — Tests on every target

High priority by decree: running tests must be easy — both languages, desktop and wasm — before any engine code accumulates. The M1/M2 FFI corpus (add, callbacks, error paths, panic containment) is the seed test suite that proves the harnesses work.

1. Rust: `cargo test` native, and `cargo test --target wasm32-unknown-emscripten` with Node configured as the cargo target runner. Known-fiddly territory (cargo has open issues around executing emscripten's .js+.wasm output pairs); timebox it, document what works and what's excluded.
2. Rust in the *browser*: emscripten test output is a .js+.wasm pair a page can load, so the script-driven browser harness from item 3 serves the same test binaries there. If this fights back past the timebox, the fallback is delegating Rust-in-browser coverage to the C#-driven FFI suite (same Rust binary, exercised from the C# side) — but that's a deviation from the "both languages, both places" decree and gets explicit owner sign-off, not a silent downgrade.
3. C#: `dotnet test` native. For wasm, the primary plan is a minimal in-host test runner reusing the same test assembly inside the M2 host projects (tests are NUnit — NUnitLite is purpose-built for exactly this embedded-runner shape) — the seed suite is FFI tests, so the wasm test host must be a wasm app with the Rust staticlib linked anyway, and the M2 hosts already are that. (XHarness — dotnet/runtime's own harness — is the fallback, with caveats recorded: it lives on a private Azure feed, not nuget.org, and its wasm test-runner entry point isn't shipped; expect to write glue.) Runs on the Node host; a browser-hosted run of the same tests (driven by a script, not by hand) completes the matrix.
4. One command (`./test-all` or similar) that runs the full matrix and reports per-target results.
5. Minimal CI: a Linux GitHub Actions job running `./test-all` (native + wasm-node at minimum; browser-in-CI can wait for M5). M4 is the first real engine code — it should land into working CI, not before it. Any CI step invoking cargo directly (fmt/clippy gates included) runs with cwd=`src/` — rustup resolves `rust-toolchain.toml` from the invocation cwd, and a root-cwd `--manifest-path` invocation silently uses the runner's default toolchain instead of the pin.

**Done when:** a deliberately-failing test fails visibly on every target it applies to, then is removed; the whole matrix is one command; CI runs it; the matrix is documented in ARCHITECTURE.md (which suites run where, and any per-target exclusions).

### M4 — Kernel: RIDs, lifecycle, modules, logging

1. RID allocator in Rust: generational slotmap, type tags, `Option` lookups — Godot's `rid_owner.h` is the design being ported, deviations deliberate. Unit tests: reuse, stale-handle detection, type confusion rejected.
2. Engine lifecycle across FFI: `buck_engine_create(config)` / `buck_engine_destroy`, owning an `Engine` struct that all subsystems hang off (no globals beyond the unavoidable). The config struct is the first hand-mirrored `#[repr(C)]` type, so the **layout-assertion test seam** lands with it (Rust exports `size_of`/`offset_of` per mirrored struct, C# compares against `Marshal.SizeOf`/`OffsetOf`) — the interim protection that lets FFI binding generation (deferred list) wait; it stays valuable afterward as the generator's output check.
3. C# `Engine` class: `Create`/`Dispose`, `PumpEvents`/`Tick`/`Render` (the latter two no-ops for now), module registry — modules declare dependencies, init in topo order, tick in registration order. Cycle detection with a real error message.
4. Logging: Rust `log` crate → records buffered in Rust, delivered to the C# log sink by the **exit-drain at the tail of every FFI call** (records-before-result, unconditionally — a failed call's diagnostics deserve delivery more, not less; the causal C# call is still on the stack when the sink fires), plus an **emit-time immediate channel** (stderr today; the seam for future network error reporting or editor-over-socket) that is zero-latency and crash-proof. Buffering (rather than a synchronous callback per log statement) is what keeps callback rule 4 honest — a `log::info!` deep inside borrowed engine state must not re-enter C#. C# logs round-trip through Rust (the `Log` facade over `buck_log`): one buffer, one ordering, one filter, one delivery path for both languages. Logging is process-scoped (the `log` crate's logger is a process global; multi-engine log separation is not a goal). (As built; the original M4 sketch drained at `PumpEvents`, upgraded mid-milestone by owner review.)
5. Determinism kernel pieces: seeded PRNG streams (kernel supplies the algorithm; stream state lives in sim state and is covered by the state hash, per the Determinism rules), tick counter, and the **determinism harness v0** — inject a recorded host-call trace (dts + events) into a toy stateful module, hash the sim state every tick (content-based), write the hash trace to a file; run twice as *separate processes* and diff (an in-process double-run can't catch .NET's per-process hash randomization). Wired into CI in this same milestone. The harness and the state-hashing convention are first-class deliverables, same standing as the golden-test infra. Design the hasher's state *traversal* as the seed of a general visitor: hashing today, but cloning, save/load serialization, and state-diffing all want the same walk over the same state (planefarer's `Dec.Recorder` is the precedent — one mechanism serving serialize, clone, and CoW). Don't build those yet; just don't design the traversal in a hash-only corner.

**Done when:** desktop host creates an engine, registers two dummy modules with a dependency between them, ticks 100 times, shuts down clean; tests cover RID edge cases, module ordering, module cycles, log routing, and the determinism replay test — and run on all targets per the M3 matrix.

### M5 — Windowing module

Before designing the event vocabulary and window API, read Godot's `DisplayServer` (`../godot/servers/display/display_server.h`) — it's a decade of accumulated "what does a windowing abstraction actually need" and we steal its shape judiciously; winit remains the implementation underneath.

1. Rust window module (cargo feature `window`) wrapping winit in pump mode (`pump_app_events`) — the engine stays callee; `PumpEvents` drives winit exactly one pump. Note winit covers desktop only: its web backend is wasm-bindgen/`wasm32-unknown-unknown`, not emscripten, so on web there is no Rust windowing layer at all (see the deferred web-event-path entry).
2. Window events → C# callbacks: resize, close-requested, keyboard (raw keycodes only for now — input mapping is a later module). The C#-facing event surface is **host-injectable**: events are plain data the host (or a test) can feed in, with the winit module being merely the desktop producer. This is the seam that makes the web event path (JS → C# injection) trivial later, and it makes event plumbing testable without a window.
3. Desktop host opens a window; close button and Escape both quit via the C# side deciding to stop the loop.
4. CI, phase two (phase one landed in M3): add the Windows build check, and the script-driven browser test runs if they weren't already CI-able at M3. Windows CI must not enter `tool.bat`'s cmd branch blindly: its on-failure `pause` (a double-click-convenience yank from planefarer) waits for a keypress — invoke via bash, or make the pause interactive-only first.

**Done when:** window opens on Linux (Wayland + X11 via winit), resize/close/key events observably reach C#, clean shutdown; CI green including the Windows build check. No unit tests for the window itself (UI exemption); event plumbing is tested via host-injected fake events.

### M6 — RLL: WebGPU init and headless clear

The renderer's foundation, proven without a window first. Items 1–3 don't touch the window and are parallelizable with M5.

1. `webgpu.h` Rust bindings (bindgen against the shared header) + wgpu-native as the desktop provider.
2. RLL API v0, RID-based, exposed to C#: instance/adapter/device init — **async-shaped per the foundation decision**: `Create` kicks off the requests, ticks pump completion, the engine reports Ready — texture create, command encoder, render pass with clear, submit, buffer readback (readback is native-only; the browser can't block on map). Just enough surface for the test below — no speculative API.

This infra is a first-class deliverable — every rendering feature from here on lands with a golden test. Golden tests run native-only for now; the per-target rendering-test story is in the deferred list. (Determinism note: readback exists for tests and tooling — render output never feeds back into sim, per the Determinism rules. GPU output is outside the sim-state hash.)

Surface path: create a surface from the M5 window, clear it to a color, and reconfigure the surface on M5 resize events (resize handling lives here, not M5 — the window module just reports; the RLL owns the surface). Surface creation is the one platform-specific seam in the RLL; keep it isolated.

**Done when:** CI is green, including the headless clear-to-color golden test with no window and no GPU-vendor assumptions (lavapipe-friendly); desktop host shows a colored window that survives resize; non-rendering suites still green on all targets.

**Done when:** one HLSL source produces the same triangle on desktop and web; golden test green.

### M9 — The mesh/pass/dispatch layer (C#)

The terminal milestone of this plan, and the layer the project owner cares about most. **The API shape gets designed in discussion before implementation** — expect strong opinions; do not design this autonomously and present a fait accompli. The default-must-be-simple principle governs that discussion: the obvious way to make a mesh and draw it should be a handful of lines that just work, with the bulk/perf paths as opt-ins from inside the same model. Also the first C#-heavy milestone and the first real test of the bulk-FFI discipline.

1. C# abstractions: Buffer, Texture, Mesh, Pipeline, shader+bindings grouping — exact shape per the design discussion above. Three constraints the design must respect regardless of shape: (a) this layer sits on the render side of the determinism boundary, so sim→render data flow is one-directional — dispatching reads sim state, never mutates it; (b) sim state refers to renderable resources by state-local IDs, never render RIDs directly (render RIDs are nondeterministic and outside the hashed state), so dispatch consults a sim-local-ID → render-RID mapping living outside the hashed state. State-local IDs are u64 — deliberately RID-width — so that mapping can be a *build-time choice*: translation layer (deterministic default) or verbatim pass-through for projects that don't care about determinism/cloning and want the perf back. The pass-through mode isn't implemented in this milestone; the width constraint and the build-time seam are what get honored now. How the mapping is *managed* — lifetimes, reaping, surviving rollback — is deliberately not core rendering's business: the core provides the seam, and management strategies live up toward userspace. And (c) resource lifetime in the easy path: allocating a resource, never assigning it to anything, and dropping every C# reference to it must not be a leak — the GC-backstopped-release entry in the deferred list is the candidate mechanism. All three are named inputs to the design discussion, not things to discover mid-implementation.
2. Shader reflection v0: extract bind group layouts from the compiled shaders so pipeline layout creation isn't hand-duplicated. (Full permutation/variant machinery is explicitly deferred.)
3. Direct pass recording with the pass boundary kept explicit as an API concept — but no render graph. There is exactly one pass in this milestone and nothing to derive an order between; a graph gets extracted when the first real second pass exists (see deferred list). No barriers exposed anywhere regardless (WebGPU has none; Vulkan-later derives them behind this same seam).
4. Bulk submission: per-frame draw data crosses the FFI as spans of blittable structs, one call per pass, not per object.
5. Depth buffer, uniform buffers, a textured quad and an untextured spinning cube (MVP matrix as a plain uniform — no camera abstraction) as the proof cases, each with golden tests.

**Done when:** textured quad and spinning cube on desktop + web, golden tests for both, zero per-object FFI calls in the frame loop (verified by a counting test, not by eyeball).

## Consciously deferred

Not forgotten — postponed, with the seam that keeps each possible noted:

- **Lighting, cameras, and "renderers" (Forward/Forward+/Deferred) entirely.** The mesh/pass/dispatch layer is the current ceiling. When renderers do arrive, the renderer-swap interface is extracted from the second implementation, not designed before the first; same for the material-model seam (surface-shader abstraction).
- **Render graph** — extracted when the first real second pass exists (shadow map or post-process). Until then, explicit pass boundaries in the M9 API are the seam.
- **Rendering tests beyond native** — browser golden tests are feasible in principle (readback is async in the browser, but an async test harness + script-driven browser run can do it), and Node may grow usable WebGPU; revisit once the native golden infra has mileage. Until then: native golden tests + manual web spot-checks.
- **Web input/event path** — winit doesn't exist on emscripten, so web events (resize, keyboard, pointer) will come from above: JS → C# host-injected events through the M5 event surface. Canvas resize is the first thing that'll need this, likely during M7–M9 manual testing; acceptable to hardcode a fixed canvas size until then.
- **Asset pipeline** (import/cook/IDs/hot-reload) — M9 uses hardcoded/generated meshes. Asset identity scheme gets decided when the pipeline exists; nothing before it serializes asset references.
- **Command-buffer FFI** — additive on top of RID + bulk-span calls if profiling demands it.
- **Pull-based event buffers** — per-subsystem retrofit if a callback path shows up in a profile.
- **Threading/job system** — everything single-threaded until it hurts, and when it does, the recorded starting stance is planefarer's production-proven model: **sim is strictly single-threaded *within* an environment; parallelism happens at whole-environment granularity** — dedicated worker threads each owning a cloned environment (Orrery's design, with its stated principles: single owner, single lock, self-contained clone/advance tasks, minimal thread communication; see `../planefarer/CLAUDE-Orrery.md`). This sidesteps the deterministic-job-scheduling problem entirely for sim. Per the clonable-state layering rule, this is a *userspace pattern the engine enables*, not an engine subsystem — the engine's obligation is only that its primitives are safe to use this way. A finer-grained job system (fixed partitioning, fixed reduction order, or explicit opt-in nondeterministic mode) stays speculative-later. Other constraints unchanged: web degrades to single-threaded, no mandatory render thread, determinism stays the default.
- **Deterministic sim math** — the path from same-machine to cross-machine/cross-target determinism. Candidate approaches, not mutually exclusive: fixed-point (planefarer's `Q32` + `Vector2Q`/`Rect2Q` are working prior art and the owner-endorsed direction — "just avoid floating-point" in deterministic mode), softfloat, or a bit-exact float libm. Until something exists, engine sim paths avoid platform libm outright — which makes this less deferrable the moment a real game sim needs transcendentals.
- **Cross-target determinism CI** — the same recorded input trace run on linux native and wasm-node, state hashes compared. The wasm-desktop target makes this nearly free once deterministic sim math is settled; blocked on that.
- **Netcode** — deliberately unresolved (the recorded stance is an honest "I dunno"). What *is* decided: the engine provides the primitives — determinism, the injectable input boundary, fast clone/checksum — and netcode consumes them as a module on top, **available but never "the one true method"**. Rollback-style approaches carry intrinsically per-game tweaks, so baking one deeply into the core is off the table. One shape worth remembering when this comes due: with parallelism, catching up doesn't require clone-plus-resimulate inside a single frame budget — multiple catching-up states can take a frame or two to converge. Early rendering semantics are unaffected by any of this.
- **Editor** — yes, eventually, and it will want reflection/data-definition/property-inspection machinery. Owner's call, recorded: that machinery is judged retrofittable, so nothing is pinned now. Engine-as-library keeps the door open — an editor is just another host.
- **Serialization / data-definition (the Dec question)** — punted entirely, on purpose. Dec is liked but intrinsically C#, and a Rust Dec that works equally well from C# is hard to imagine. Possible direction: Rust-side serialization, if/when it exists, mimics Dec *behavior* (conventions, semantics) without being Dec; full form unknown. One requirement to carry regardless: planefarer serializes **live coroutine state** (Dec's RecorderEnumerator records compiler-generated iterator state machines, closures, and LINQ enumerators) and the Arbor AI layer depends on it — suspended coroutines as sim state is a real long-term want, so the eventual serialization story needs an answer for it, or an explicit decision not to support it. The M4 traversal-as-visitor note stands regardless of how this resolves.
- **Input-trace record/replay** — not the engine's problem, recorded as such. Replay features — bug-report traces, user-facing replays, planefarer-style crashloop mode (auto-capture a reproducing replay on first error; the biggest payoff of the determinism investment) — are userspace, built on the determinism contract. The engine's entire obligation is already met by the boundary design: inputs are injectable, so recording is just writing down what you inject. The M4 harness keeps a trace format as its own private test infrastructure; nothing about it is a product surface or an engine API.
- **Changelog tooling** — planefarer's `RN:` mechanism is liked and likely gets adopted: commit messages carry `RN: <single changelog line>` entries with category prefixes, and a release tool collects them into CHANGELOG sections for manual curation. Note the design intent: an `RN:` line is a *single changelog line* that augments the commit description — it does not replace it. Until this exists, the manual CHANGELOG step in CLAUDE.md stands.
- **Profiling and benchmarking infrastructure** — planefarer treats these as first-class and Buckminster inherits the stance: a cheap pluggable `using var p = Prof.Sample()` scope idiom in every system, test-attached trace profiling, and a benchmark harness whose flagship fixture is *environment clone cost* (planefarer literally benchmarks `Dec.Recorder.Clone(env)` empty-vs-populated). Clone speed is a stated design goal here, so the day environments exist, clone cost gets a benchmark, not vibes.
- **Determinism enforcement tooling** — the escalation path beyond planefarer's "don't rely on Dictionary order, this is your problem" convention (which is the baseline until these exist). In rough order of value-per-effort: (1) `DeterministicDictionary<K,V>`, IndexMap-style — dense insertion-ordered entry array, hash table used only as a lookup index, so iteration never observes `GetHashCode` and no comparer is needed; insertion order is deterministic whenever call order is, which determinism mode already guarantees. (2) Roslyn analyzers scoped to sim assemblies — off-the-shelf BannedApiAnalyzers (`Dictionary.GetEnumerator`, `HashSet` enumeration, `string.GetHashCode`, `System.Random`, `DateTime.Now`, `Guid.NewGuid`, …) plus a small custom analyzer for `foreach`-over-`IDictionary` shapes; sim-code-in-separate-assemblies (which modules encourage anyway) makes the strict/lax split a one-line build property. Cecil-based IL auditing reserved for third-party assemblies we don't compile. (3) Factorio-style **heavy mode** on the M4 harness: per-subsystem hashes every tick so a divergence names its subsystem and tick immediately, state-dump-and-diff on mismatch. (4) Planefarer's proven verification kit, ported in spirit: double-replay verify (`Orrery.Verify` re-simulates from a snapshot twice and compares checksums), a checksum **diff** that names the diverging field (`Dec.Recorder.ChecksumDiff` — a hash that only says "mismatch" wastes the detection), and the serialization-aliasing lint (shared-reference detection repurposed to catch inputs aliasing mutable sim state). (5) Stable-ID identity: planefarer's per-environment serialized monotonic `stableId` is the working answer to "what do you order class instances by" — deterministic, survives clone and save/load, backs an opt-in `StableComparer` rather than making entities globally ordered. A forked/annotated BCL was considered and rejected: permanent upstream-tracking burden, wasm runtime-pack complications, and the above gets ~all the value.
- **Clonable / parallel / checksummable game state** — long-term but important; a stated priority for whenever a scenegraph-or-equivalent exists. Sim state that is cheaply clonable (CoW where relevant), executable in parallel (clone the state, run four copies with the same input, get four bit-identical checksums), and checksummable cross-platform (content-based; version-durability explicitly not required). Clone speed is an explicit goal — as fast as possible, but not by compromising the other goals here; simplicity still outranks it per the governing principle. A layering rule governs all of this: the *engine* provides the primitives — content-based hashing/traversal, deterministic allocation, PRNG-in-state, the ID seams — while the machinery that *manages* clones (snapshot pools, catch-up lanes, GPU-resource claim/reap schemes like planefarer's `PersistentRenderingManager`) lives several layers up toward userspace, because whole models won't use any of it and must not pay for it. Zero-cost-when-unused is a design constraint on the engine-side pieces. Beyond that, two things are decided now: clone management lives **in C#**, with "a Buckminster environment" as a first-order C# concept — the unit that gets cloned, checksummed, and run in parallel, containing all sim state including PRNG stream state — and access is via a **thread-local current-environment global** (Ghi's `Environment.Current` is the exact shape), *not* an environment handle threaded through every signature. Thread-local composes naturally with parallel clone execution (each worker sets its own current) and is trivially correct on single-threaded wasm; the `ThreadLocal` vs `AsyncLocal` question only arises if sim code ever goes async, which would be its own determinism problem first. Planefarer's Ghi system (`../planefarer/project/thirdparty/ghi/`, especially `Cow.cs` — revision-tagged copy-on-write handles that clone as part of an Environment) is the reference shape — though its self-documented `operator=` footgun ("undefined state, perhaps it will change! you will never know") is exactly what the default-must-be-simple rule forbids shipping as the default experience; the Buckminster version either fixes that or fences it off as the expert path. Deliberately open questions, to be settled when this work starts, not now: whether an unset current environment falls back to a default or errors, how environments relate to engine instances and modules, and where checksum computation runs. Seams held from day one: the M4 content-based state-hash convention is what grows into the checksum; no process-global mutable sim state; PRNG stream *state* lives inside the sim state so clones carry their randomness with them; sim-state-internal references are state-local IDs rather than shared-allocator RIDs — RID-width u64s, per the M9 constraint — so a clone is self-contained. Cross-platform checksumming inherits the deterministic-sim-math dependency.
- **Polyglot layering (really long-term)** — the aspiration, explicitly not worried about anytime soon: any layer of the stack implementable in any language (a Python render backend under the Rust RLL, a C# render frontend, a Rust scenegraph over it, game logic in something else entirely), including someday-support for languages beyond C# and someday-removing C#. What today's decisions already buy: the flat C ABI as the one lingua franca, the narrow type convention (blittable/RID/span/key/vtable, no Variant ever) that keeps per-language bindings boring, `#[buck_trait]` vtables that don't care what runtime a fn pointer lands in, and the coarse/bulk boundary rule as the polyglot survival discipline. What it costs when it happens, priced now: per-language runtime embedding (the hard part — co-resident GCs, threads, signals), one binding-generator emitter per language (the generator's dump stays language-neutral data so new languages are new emitters, never a redesign), and a per-language exception-containment convention mirroring the callback rules. Eligibility rule: a language must support being embedded as a library; on web that's via emscripten, where most embeddable runtimes are happy — .NET is the odd one out (library on desktop, host-only on web), so .NET keeps the web host seat while it exists. Near-term consequences, decided in the M4 module-registry discussion: Rust (or any-language) modules arrive as FFI-backed `IModule` proxies and the registry stays C# — it is ~100 lines of test-pinned policy, explicitly priced as a cheap reimplementation if composition ever moves; the one C#-ism to keep confined is dependency identity by `System.Type`, which stays inside the registry and never becomes a general currency, since any multi-language registry replaces it with name/ID identity.
- **Audio, input-mapping module, GUI toolkit interop beyond the window itself.**
- **Mac/mobile targets** — kept possible by winit + WebGPU-everywhere + no Win32/Wayland assumptions in module interfaces; not built.
- **Vulkan/DX/GL RLL backends** — the pass-boundary tier is the seam; wgpu-native already covers them underneath in the meantime.
- **FFI binding generation, and C#-implemented Rust traits** — the successor to the deliberately-hand-written M1 boundary; designed now (surveyed against the Godot checkout in depth), built later. Godot's two systems were evaluated and rejected with reasons: GDExtension's string-keyed method/virtual lookup, signature-compatibility hashes, and five versioned ABI structs all exist so precompiled extension binaries survive engine changes — a problem compile-time composition doesn't have; the mono module's GCHandle weak/strong-swap bridge is GC-timed native destruction, against our deterministic-lifetime policy; and its engine→C# virtual dispatch is a per-call string-compare chain Godot's own comments call temporary. What Godot *validates*: blittable-structs-by-pointer as the hot path (its ptrcall core), one generator from one source of truth, and function-pointer tables for cross-boundary virtuals. Steal those three; reject the registry, the Variant layer, and the GC lifetime machinery.
  - **Chosen shape: Rust source is the single truth, and generation covers only the raw boundary.** The friendly C# layer (M4's Engine and up) stays hand-written — that's where API design lives; what gets generated is exactly what nobody should hand-sync: the `NativeMethods`-layer imports, mirrored `#[repr(C)]` structs/enums (killing the "keep in sync" comments), and trait/callback glue. Mechanism: `#[buck_export]` on an idiomatic Rust fn generates the `extern "C"` + `ffi::guard` wrapper (M1's rails mechanized — the "macro or helper fn" deliverable finally becoming the macro) and registers an inventory entry; `#[buck_struct]`/`#[buck_enum]` implement a metadata trait that inventory entries reference for type identity (no token-stringification fragility); a workspace bin target links the crates and dumps the inventory sorted (deterministic output for the staleness check), and a generator emits the C# side (`[LibraryImport]` bindings with `FfiCode` returns and out-params, `StructLayout` mirrors, span helpers) as a SCons codegen step. Generated C# is checked in, with a CI check that it's current. Dump rules: inventory registration sits behind a dump-only cargo feature (never in shipped artifacts, and the does-registration-work-on-emscripten question never has to be answered); the dump build enables the union of module features so gated exports can't silently vanish; and the export surface is target-uniform — per-target behavior lives inside Rust bodies, never in the export list (one C# assembly serves all targets anyway). The generator stays small *because* the convention is narrow: blittable scalars, mirrored structs, RIDs, span pairs, u64 keys — anything else is a loud generator error, never a new marshalling layer. No Variant, ever.
  - **Traits (C# implementing Rust traits)**: `#[buck_trait]` on an FFI-expressible Rust trait generates a `#[repr(C)]` vtable struct (one `extern "C"` fn pointer per method, u64 userdata key, plus a release fn pointer) and a Rust proxy type implementing the trait by forwarding through it; the C# side generates the matching interface plus `[UnmanagedCallersOnly]` thunks (each the canonical try/catch + `CallbackExceptionStash` body) and registration glue over `CallbackTable`. This is M1's callback rails generalized from one function pointer to a struct of them — M2 proving the callback round trip on wasm de-risks the mechanism in kind (a vtable of pointers is mechanically identical to one passed as a parameter). **FFI-expressible is enforced, and Result-shaped is part of it**: exportable trait methods take blittable/mirrored/RID/span/key args and return `Result`-shaped signatures — settled now, not at build time, because a C# exception surfacing as a proxy panic would make "engine state is suspect" a routine error path mid-tick, and because the hand-written M4/M5 trait-shaped surfaces are this generator's first conversion corpus and must be born convertible. Generated trait interfaces are deliberately **public** C# surface (they exist to be implemented by game modules — they *are* API); the internal-never-public rule scopes to the raw import layer. Dispatch is one indirect call per method; trait interop is for coarse extension points (module hooks, host services), not per-entity hot paths — the bulk-span rule is unchanged.
  - **Lifetime**: Rust→C# objects stay RIDs with explicit destroy (locked decision, unchanged). C#→Rust (trait impls and callbacks): the `CallbackTable` entry is the strong reference keeping the C# object alive; the Rust proxy owns the registration and its `Drop` invokes the release fn pointer, which unregisters the key. What's rejected from Godot is *GC-driven* lifetime (weak handles, finalizer-scheduled destruction) — the table gives the same aliveness guarantee with deterministic release timing, loud stale-key detection, and a debug-build leak check (table asserted empty at engine destroy). Two hazards pinned now because naive ownership gets them wrong: (1) **reentrant unregistration** — a hook unregistering itself from inside the very dispatch that invoked it is the *normal* case for extension points, and callback rule 4 is literally unsatisfiable if the engine holds `&mut` proxies while dispatching; so proxies are shared-owned (`Rc`), dispatch iterates a snapshot of the hook list, and unregistration mid-dispatch is deferred to a safe point at dispatch end — still deterministic, just "end of dispatch" rather than "instant". (2) **The release channel cannot fail**: it fires from `Drop` (possibly during unwind), so there is no error return — a nonzero or a stashed exception from a release thunk is a bug that logs loudly or aborts, never gets dropped on the floor. And no proxy `Drop` may run at process exit after the .NET runtime is gone — explicit engine destroy (M4 lifecycle) already guarantees teardown ordering.
  - **Off-the-shelf tools** (re-verify their state when this lands): csbindgen does mechanical `extern "C"`→C# transcription well but knows nothing of the guard/FfiCode/CallbackTable rails and has no trait story — an emission reference, not the system; interoptopus validates the inventory→generator architecture but imposes its own conventions; uniffi (+ the third-party C# backend) has real foreign-implemented-trait support — precedent worth reading — but its RustBuffer serialization violates the blittable/bulk discipline and its error model would displace ours. The conventions here are narrow enough that owning a small generator costs less than bending the engine to a general tool.
  - **Timing**: the window opens after M3 (all targets green, tests everywhere to protect the conversion); the owner's instinct is after web export works, and nothing forces it earlier because the interim seam removes the silent-failure pressure: **layout-assertion tests** (Rust exports `size_of`/`offset_of` per mirrored struct; C# compares against `Marshal.SizeOf`/`OffsetOf`) land with the first hand-mirrored struct in M4 and stay valuable after the generator exists (they verify its output too). Hard deadline: before M9's bulk-struct surface, where hand-maintenance stops being merely annoying.
- **GC-backstopped release of render-side resources** — a deliberate, scoped exception to the deterministic-lifetime stance above, to revisit when the M9 layer is designed (it's constraint (c) there). The motivating case (owner's): allocate an index buffer, never assign it to anything, drop every C# reference — that must not be a leak, and under default-must-be-simple, forgetting to Dispose cannot be a punishable offense in the easy path. The determinism rules permit the carve-out by construction: what's banned is finalizers/Drop mutating *sim* state, and render RIDs already live outside the hashed state on allocator instances whose call order is allowed to be nondeterministic — so GC-timed release of a render resource breaks nothing. The shape to evaluate is much simpler than Godot's weak/strong swap because no engine→C# callback ever targets these wrappers (dispatch reads sim state, not wrapper objects), so only one direction exists: the C# wrapper (Buffer/Mesh/…) holds the RID; explicit `Dispose` is the immediate-release path; the finalizer is the backstop, and it never touches the FFI (wrong thread) — it enqueues the RID on a pending-release queue drained at a safe point in `PumpEvents`/`Tick`, the same drain-at-a-safe-point shape as M4's log buffering, keeping the FFI single-threaded. Stale-destroy safety comes free from RID generation checks; debug accounting at engine destroy can still distinguish "GC reclaimed it" from "genuinely leaked". Generalizing to any Rust-owned, non-sim resource surfaced to C# is the eventual goal; sim-side resources stay explicit forever. The dividing line is sim-vs-non-sim, *not* C#-vs-Rust (per the language-split decision, C# render/UI code is expected in quantity and is the primary consumer of these wrappers) — the constraint attaches to the resource's role, not to which language holds the reference. The C#→Rust direction (trait impls, callbacks) keeps its explicit table-held lifetime from the entry above regardless of side, for a structural reason rather than a determinism one: the GC cannot see a reference held from Rust, so a table entry keeping the object alive until an explicit release is the only correct shape there.
- **Prebuilt standalone host binaries** — the desktop host project template *is* the product until someone other than me exists.

## Known risks, accepted

- **Toolchain coupling** (rustc's prebuilt emscripten std ↔ emsdk ↔ .NET workload, including exception-handling ABI) — mitigated by M2-first and pin-as-a-matched-set with link-and-run verification.
- **Wasm test harness fiddliness** — `cargo test` on emscripten and NUnit-under-wasm are both workable but under-travelled paths; M3 exists precisely to absorb this pain while the codebase is tiny. Fallbacks are named per language so a timebox expiry can't quietly orphan the requirement: C# falls back from in-host-runner details to XHarness (or vice versa); Rust falls back from libtest to `harness = false` with a libtest-mimic-style runner, or in the worst case Rust test entry points exposed over FFI and driven by the existing wasm hosts.
- **`wasmconsole` is experimental** — the Node-hosted template exists through current SDKs but Microsoft has killed adjacent experimental wasm workloads before (`wasi-experimental`, dropped in .NET 9). Mitigation: the template is sugar over the `wasm-tools` runtime pack + WasmAppBuilder targets, so a generated .csproj keeps working if the template dies; worst case is a hand-written Node host over the same publish output. Install channel recorded in `docs/wasm-toolchain.md`.
- **webgpu.h divergence** between wgpu-native and emdawnwebgpu — both track upstream webgpu-headers but at different revisions of a still-moving header. Mitigation: pin one webgpu-headers revision and pick the wgpu-native and emdawnwebgpu releases that match it as a pair; upgrades happen in lockstep or not at all. The RLL avoids vendor extensions; any unavoidable use gets an explicit `// vendor:` comment so divergence is greppable.
- **Reverse P/Invoke cost on wasm** — accepted for event-shaped callbacks; the bulk-FFI rule keeps it out of hot paths.
- **HLSL→WGSL translation gaps** (DXC/Naga corner cases) — accepted; shaders stay simple until the toolchain has mileage, and the triangle/quad/cube progression shakes it out incrementally.
- **Float determinism beyond one machine is genuinely hard** — glibc dispatches libm per-CPU at load time and changes results across versions; .NET BCL helpers branch on hardware vector support; tiered JIT compilation has historically changed float results mid-process (dotnet/runtime#1119); wasm NaN payloads are spec-level nondeterministic. Accepted by scoping the v1 promise to same-build-same-target-same-machine and holding the keep-the-door-open policies (no fast-math, no libm in sim paths, NaN-in-sim-fails-the-hasher). Cheap belt-and-suspenders: replay-verification CI runs pin `TieredCompilation=0`. The full solution is deterministic sim math (deferred) — most likely fixed-point, which sidesteps the entire float question.
